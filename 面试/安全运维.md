# 安全运维面试题

1.mysql5.7和8.0在用户管理上区别

密码生成与策略：

MySQL 5.7：在数据库初始化完成后，会自动生成一个root@localhost用户，并且这个root用户的密码是随机产生的，而不是空密码。同时，MySQL 5.7支持用户设置密码过期策略，要求用户在一定时间过后必须修改密码。密码的过期策略可以通过default_password_lifetime参数进行设置，例如设置密码180天过期：Set global default_password_lifetime=180;。

MySQL 8.0：在密码管理方面，虽然也支持密码过期策略，但MySQL 8.0的重点更多地放在了性能优化和新的功能特性上。

 

用户账号锁定与解锁：

在MySQL 5.7中，管理员可以使用ALTER USER语句来锁定或解锁用户账号。例如，锁定用户testuser的账号：ALTER USER ‘testuser’@’%’ ACCOUNT LOCK;，解锁用户账号：ALTER USER ‘testuser’@’%’ ACCOUNT UNLOCK;。

MySQL 8.0也支持类似的操作。

 

认证方式：

MySQL 5.7.2之前的版本使用password的hash值来判断使用的认证类型，而5.7.2及之后的版本开始使用mysql_native_password作为默认的认证方式。

MySQL 8.0也沿用了这种认证方式，但在其他方面进行了优化和改进。

 

性能优化：

虽然用户管理不是MySQL 8.0的主要性能优化点，但MySQL 8.0在读写性能、IO绑定性能和高并发性能方面都有明显的优化，相比MySQL 5.7有更高的吞吐量和更低的延迟。这种性能优化也间接地提升了用户管理的效率。

 

默认字符集：

MySQL 8.0将默认字符集从latin1改为utf8mb4，这样可以支持更多的Unicode字符，包括emoji表情。虽然这与用户管理不直接相关，但字符集的变化可能会影响存储用户信息（如用户名、密码等）的方式和效率。

 

错误日志：

MySQL 8.0对错误日志进行了重构，使其更加清晰和易于分析。这有助于管理员更快地定位和解决问题，从而提高了用户管理的效率和准确性。

 

总的来说，MySQL 5.7和MySQL 8.0在用户管理方面的主要区别在于密码生成与策略、用户账号锁定与解锁、认证方式以及性能优化等方面。在选择使用哪个版本时，需要根据具体的业务需求和系统环境进行权衡和选择。

 

2.mysql主从复制延时，怎么优化

检查网络延迟：

使用ping命令或其他网络工具来检查主从服务器之间的网络延迟。

尽可能使用高速网络连接，例如千兆以太网连接或更高速的连接。

优化网络带宽分配，确保主从数据库之间的网络连接稳定且带宽充足。

如果数据中心之间的网络延迟比较大，考虑将主从数据库部署在同一数据中心或就近的数据中心。

 

优化主从复制参数：

调整binlog_cache_size和max_binlog_cache_size参数的值，以提高写入binlog的效率。

启用binlog_format=ROW，这通常比STATEMENT或MIXED格式在主从复制时性能更好。

考虑使用sync_binlog=N（N>1）来减少磁盘I/O操作，但这样做可能会增加数据丢失的风险（在N个事务之后同步binlog到磁盘）。

 

使用多线程复制：

在MySQL 5.6及更高版本中，可以使用多线程复制来提高从库的复制速度。通过设置slave_parallel_workers参数的值来启用多线程复制。

 

硬件和资源配置：

增加从服务器的硬件资源，如CPU、内存和磁盘I/O性能，以提高从库处理主库binlog的能力。

使用SSD硬盘替代传统的HDD硬盘，因为SSD具有更高的I/O性能。

 

优化查询和事务：

减少长时间运行的事务，因为大事务可能导致从库复制延迟。

优化查询性能，减少从库上的查询压力，以便它能够更有效地处理复制任务。

 

使用半同步复制：

考虑使用半同步复制代替异步复制。半同步复制确保至少有一个从库已经接收了主库的binlog事件，从而提高了数据的可靠性和一致性。虽然这可能会稍微增加一些延迟，但它可以减少数据丢失的风险。

 

增加从库数量：

在需要更高读取性能或更高容错性的场景中，可以考虑增加从库的数量。这可以通过将读取负载分散到多个从库上来减少单个从库的复制压力。

 

监控和日志：

使用MySQL的监控工具（如SHOW SLAVE STATUS命令）来定期检查复制状态和延迟情况。

检查从库的错误日志，查找可能导致复制延迟的潜在问题。

 

分区数据库：

如果可能的话，将数据库分成多个区（或表），并让每个从库只复制自己所需要的数据区。这可以有效地减少排队堵塞和网络传输等方面的延迟问题。

 

读写分离：

通过将读操作分散到从库上，减少主库的负载，并允许从库专注于处理复制任务。这可以通过使用代理（如ProxySQL）或其他中间件来实现。

 

请注意，在尝试任何优化之前，最好先备份您的数据库和配置，并在测试环境中验证更改的效果。此外，每个环境的优化需求都可能不同，因此需要根据具体情况进行调整。

 

3.说说你对k8s的理解

K8s，即Kubernetes，是一个开源的容器编排引擎，由Google开发并开源，旨在自动化部署、扩展和管理容器化应用程序。它使用Go语言编写，托管在云原生计算基金会（CNCF）之下。K8s的主要功能包括容器编排、容器运行时、以容器为中心的基础设施编排、负载平衡、自我修复机制和服务发现等。

 

K8s的基本架构分为两部分：控制平面和节点或计算机。控制平面负责集群的管理控制中心，包括API服务器、调度程序、控制器管理器等组件。节点则负责运行实际的容器应用，每个节点可以是物理机或虚拟机，并且拥有自己的Linux环境。节点上运行着由容器组成的Pod，Pod是K8s中运行应用的基本单位。

 

K8s的主要特点包括：

 

自动化：K8s支持自动化部署、自动重启、自动复制、自动伸缩/扩展等功能，大大简化了应用程序的部署和管理。

可移植性：K8s支持公有云、私有云、混合云和多重云，使得应用程序可以在不同的云环境中无缝迁移。

弹性伸缩：K8s可以根据需要自动对集群中正在运行的容器数量进行调整，实现资源的动态分配。

服务发现和负载均衡：K8s通过内置的服务发现功能，为每个Service配置DNS名称，并允许集群内的客户端直接使用此名称发出访问请求。同时，Service还通过iptables或ipvs建立负载均衡机制，实现请求的负载均衡。

自我修复：K8s具有自我修复能力，例如支持容器故障后自动重启、节点故障后重新调度容器等功能。

K8s的组件包括Master组件和Node组件。Master组件提供集群的管理控制中心，包括API服务器、ETCD（一个高可用的键值存储系统，用于保存K8s集群的状态）、kube-controller-manager（控制器管理器）、cloud-controller-manager（云控制器管理器）和kube-scheduler（调度程序）等。Node组件则包括kubelet（节点代理）、kube-proxy（网络代理）和容器运行时引擎（如Docker）等。

 

总的来说，K8s是一个功能强大的容器编排引擎，通过自动化部署、扩展和管理容器化应用程序，提高了应用程序的可靠性、可移植性和可扩展性。

 

4.用了k8s之后k8s会不会节省？

资源优化和节省：

Kubernetes通过自动扩展和调度可以确保集群中的资源得到充分利用。它可以根据工作负载动态地增加或减少Pod（容器组）的数量，从而优化资源的使用。

Kubernetes还提供了资源配额和限制的功能，可以确保应用程序不会过度使用资源，避免资源争用和浪费。

 

成本节省：

虽然Kubernetes本身并不直接降低硬件成本，但它通过优化资源使用和提高应用程序的可靠性，可以减少因资源浪费和故障导致的额外成本。

在云环境中，Kubernetes可以与云提供商的自动扩展和预留实例等功能相结合，进一步降低计算成本。

 

时间节省：

Kubernetes提供了声明式的API和配置管理，使得应用程序的部署、更新和扩展变得更加快速和简单。这可以大大减少手动配置和管理工作的时间。

通过Kubernetes的滚动更新和蓝绿部署等功能，可以在不中断服务的情况下进行应用程序的升级和更新，进一步节省时间。

 

维护和管理的节省：

Kubernetes提供了统一的容器编排和管理平台，可以简化应用程序的部署、监控、日志和故障排除等任务。这可以减少对多个工具和系统的依赖，降低维护和管理的复杂性。

Kubernetes的社区非常活跃，有大量的文档、教程和最佳实践可供参考，这可以帮助开发人员和运维人员更快地掌握和使用Kubernetes。

 

可扩展性和可移植性的节省：

Kubernetes是一个开源的、标准化的容器编排引擎，它支持多种容器运行时和云提供商。使用Kubernetes可以确保应用程序的可扩展性和可移植性，从而避免了因平台锁定或技术变更而导致的额外成本和时间消耗。

7.nginx 请求，发现nginx 主机上timewait数量太多，会造成什么影响？如何优化？

资源消耗：过多的TIME_WAIT状态会占用服务器的资源，包括内存和文件描述符。当资源被大量占用时，可能会影响Nginx的性能，甚至导致服务不可用。

 

端口耗尽：由于TIME_WAIT状态的连接会占用端口，当TIME_WAIT连接数量过多时，可能会导致端口耗尽，使得新的连接请求无法被处理。

 

调整TCP参数：

tcp_fin_timeout：这个参数定义了操作系统关闭一个连接前等待多长时间。你可以根据实际情况适当调整这个值，以减少TIME_WAIT状态的持续时间。

tcp_tw_reuse：这个参数允许系统重用处于TIME_WAIT状态的连接，从而减少新的连接请求所需的资源。你可以通过设置sysctl -w net.ipv4.tcp_tw_reuse=1来启用它。

tcp_tw_recycle：这个参数用于快速回收TIME_WAIT状态的连接。但是，在某些情况下，启用这个参数可能会导致问题，因为它可能会错误地回收仍然有效的连接。因此，在启用之前，你需要确保它适用于你的网络环境。

tcp_max_tw_buckets：这个参数定义了系统同时保持的TIME_WAIT状态连接的最大数量。你可以适当增加这个值，以允许更多的TIME_WAIT连接同时存在。但是，请注意，这并不能从根本上解决TIME_WAIT数量过多的问题，只是延缓了问题的出现。

 

使用长连接：对于HTTP/1.1和HTTP/2协议，你可以考虑使用长连接（Keep-Alive）来减少连接的创建和关闭次数，从而减少TIME_WAIT状态的出现。在Nginx中，你可以通过调整keepalive_timeout参数来启用和配置长连接。

 

负载均衡：如果Nginx主机上的请求量非常大，你可以考虑使用负载均衡技术将请求分发到多个Nginx服务器上，以减少单个服务器的负载和TIME_WAIT状态的数量。

 

检查应用程序：有时候，TIME_WAIT状态过多可能是由于应用程序的行为导致的。例如，应用程序可能频繁地创建和关闭连接，或者没有正确地关闭连接。你可以检查应用程序的代码和配置，确保它正确地使用了连接并关闭了不再需要的连接。

 

监控和日志：定期监控Nginx的性能和TIME_WAIT状态的数量，以便及时发现和解决问题。同时，检查Nginx的日志文件，查看是否有与TIME_WAIT状态相关的错误或警告信息。

 

8.kubelet的作用是？

Pod生命周期管理：Kubelet会接收来自API Server的指令，确保本节点上运行的Pod达到期望的状态。这包括创建、启动、停止或删除Pod中的容器。

容器运行时交互：Kubelet与容器运行时（如Docker、containerd、CRI-O等）进行通信，执行实际的容器操作，例如拉取镜像、创建容器、监控容器状态以及清理不再需要的容器资源。

健康检查：Kubelet会监控并报告容器及Pod的健康状况。它通过HTTP GET请求、命令执行或者端口检查等方式实现健康检查，并根据结果采取相应行动，如重启容器。

资源管理：Kubelet确保节点上的容器按照其资源配置要求运行，管理和限制CPU、内存、磁盘和网络资源使用情况。

卷管理：Kubelet协调和管理Pod使用的存储卷，包括挂载和卸载持久化存储卷。

Node状态报告：Kubelet会定期向API Server汇报节点资源使用情况、运行的Pod列表以及节点的总体健康状态。这样，master节点就能知道整个集群所有节点的资源情况，这对于Pod的调度和正常运行至关重要。

总的来说，Kubelet是Kubernetes集群中不可或缺的组件，负责管理和维护集群中的容器和Pod，确保它们能够按照预期的状态和资源配置要求运行。

 

9.pod重启策略有哪些，DaemonSet一般适用于哪种重启策略？

Pod的重启策略主要有三种：

 

Always：这是默认的重启策略。无论容器退出的状态码是什么（包括0，表示成功退出），kubelet都会自动重启该容器。也就是说，只要Pod没有被删除或者节点未发生故障，即使容器由于错误或非0退出码停止运行，kubelet也会不断地尝试重启容器。

OnFailure：当设置为OnFailure时，kubelet仅在容器以非0退出码退出时才重启容器。如果容器正常退出（退出码为0），kubelet将不会重启该容器。

Never：设置为Never时，kubelet将不对任何情况下终止的容器进行重启。一旦容器停止运行，不论其退出码为何，kubelet都不会干预，容器将保持终止状态。

对于DaemonSet，由于其主要功能是确保集群中的每个节点上都运行一个Pod的副本，因此它通常需要保证容器的持续运行。因此，DaemonSet的重启策略通常应该设置为Always，以确保在容器因故障或其他原因停止时，能够自动重启并恢复服务。

13.prometheus自定义监控项有哪些？

应用程序性能指标：

响应时间：监控应用程序处理请求所需的时间。

吞吐量：监控应用程序在单位时间内处理的请求数量。

错误率：监控应用程序返回错误响应的比例。

资源使用情况：如CPU、内存、磁盘和网络的使用情况。

 

业务特定指标：

订单处理速度：监控订单从接收到完成所需的时间。

用户活跃度：监控活跃用户的数量或用户与应用的交互频率。

库存水平：监控产品的库存量，以便及时补货或调整销售策略。

 

系统级指标：

系统负载：监控系统的平均负载，以确定是否有过多的进程正在运行。

文件系统使用情况：监控磁盘空间的使用情况，以防止磁盘空间耗尽。

进程状态：监控特定进程的状态，如是否正在运行、占用的资源等。

 

网络指标：

网络带宽使用情况：监控入站和出站的网络流量。

网络延迟：监控网络请求和响应之间的延迟时间。

网络错误率：监控网络请求中发生错误的比例。

 

自定义服务监控：

监控特定服务（如数据库、缓存服务器、消息队列等）的性能和可用性。

监控服务的特定指标，如数据库的查询性能、缓存的命中率等。

14.prometheus架构是什么？

一个或多个prometheus服务器，用于抓取和存储时间序列，以及一个可选的grafana服务器用于数据可视化，exporter收集不同系统和服务的指标，AlertManager发送告警。

 

Prometheus Server：这是整个架构的核心，以进程的方式启动，并使用多进程和多线程实现监控数据的收集、计算、查询和更新。

Exporter：Exporter是Prometheus的一类数据采集组件的总称。它负责从目标处搜集数据，并将其转化为Prometheus支持的格式。

Push Gateway：主要用于短期的jobs。由于这类jobs存在时间很短，可能在Prometheus来pull之前就消失了，所以此时采用由job主动将监控数据推送到Push Gateway，Prometheus server定期从Push Gateway拉取数据。

Grafana：这是一款强大的数据可视化工具，可以通过PromQL查询语句从Prometheus Server获取数据，并生成各种可视化监控图。

AlertManager：用于处理由Prometheus服务器发送的告警。它支持多种告警通知方式，如邮件、Slack、PagerDuty等，并且可以进行告警的静默、抑制、聚合等操作。
